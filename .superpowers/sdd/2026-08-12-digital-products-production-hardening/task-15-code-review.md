# Task 15 Code Quality Review

## Verdict

**FAIL** — three P1 release-blocking correctness/validation issues remain. The absent external provider fixture is an expected rollout blocker, but the committed harness does not reliably prove when that blocker has been cleared.

## Findings

### P1 — The acceptance specs do not execute the required end-to-end state transitions

**Evidence:** `apps/web/e2e/digital-products.spec.ts:32-80` visits pre-seeded URLs and asserts broad text such as `ready|published|active`, `shipping|pickup`, and `refund|dispute|resend|delivery`. It never creates/configures/publishes a product, starts or completes Stripe Checkout, verifies a delivered email, follows a newly issued access link, consumes download grants, replaces an asset, issues refunds, drives dispute webhooks, injects a delivery failure, or invokes resend. For the most important invariants, `apps/web/e2e/digital-products.spec.ts:82-99` merely searches an arbitrary local text file for required phrases. A file containing those phrases passes without any provider action or application-state verification.

**Impact:** The Task 15 Playwright command can report success while every required commerce, delivery, grant, replacement, refund, dispute, and retry journey is broken. This fails Task 15 Step 2 and the Definition of Done's real Stripe/Resend acceptance requirement.

**Remediation:** Replace phrase-based evidence attestation with executable journeys or a structured, schema-validated evidence manifest generated by those journeys. The tests should perform the UI/API/provider actions, capture resulting safe provider/application IDs and timestamps, and query/assert the authoritative database/application state after each transition. At minimum, reject hand-authored evidence that has no per-step identity, provider event linkage, state assertions, and run provenance.

### P1 — Missing acceptance configuration exits successfully and no release gate enforces zero skipped tests

**Evidence:** Both suites apply file-level `test.skip` when `MYRIVO_DIGITAL_ACCEPTANCE_FIXTURE` is absent (`apps/web/e2e/digital-products.spec.ts:23-24`, `apps/web/e2e/digital-products-accessibility.spec.ts:27-28`). The recorded release command therefore exits zero with all 12 tests skipped. The runbook only states in prose that skipped tests are insufficient (`docs/runbooks/digital-products.md:129-132`). CI does not supply or validate either digital acceptance variable and simply runs the general Playwright command when unrelated Supabase/owner secrets exist (`.github/workflows/ci.yml:17-20,37-44`). Playwright config has no zero-skip enforcement (`apps/web/playwright.config.ts:7-34`).

**Impact:** Automation cannot distinguish a completed acceptance gate from a completely unconfigured one. A PR/deploy pipeline can remain green and the documented command can be copied as “passing” even though no digital acceptance test ran.

**Remediation:** Add a dedicated release-gate script/job that fails before Playwright unless the non-production fixture and evidence inputs exist and validate, runs only the digital suites, and fails if any test is skipped (for example via a custom reporter/result parser or explicit required-mode setup). Keep optional PR smoke behavior separate from the required promotion/rollout gate and record the successful zero-skip artifact.

### P1 — The new security suite checks source-code substrings rather than security behavior

**Evidence:** `apps/web/tests/digital-products-release-security.test.ts:25-32` considers origin, authentication, tenancy, UUID handling, and body bounds covered when four files merely contain selected strings. It omits other digital asset mutations, including `apps/web/app/api/products/digital-assets/[assetId]/replace/route.ts` and mutation handlers in `apps/web/app/api/products/digital-assets/route.ts`. Lines 34-55 similarly infer byte/decompression safety from implementation-token presence, lines 57-71 infer response hardening/rate limiting from names and a narrow `storage_path:` substring, and lines 86-99 infer schema/runtime index safety by searching migration text. None sends hostile requests, observes responses/logs, exercises throttling, attempts MIME/decompression abuse, or checks query plans.

**Impact:** Renaming a helper breaks the suite despite unchanged behavior, while dead/unreachable calls or insecure behavior can pass it. The suite cannot substantiate Task 15 Steps 1 and 4 or the claim that public outputs and logs contain no private delivery material.

**Remediation:** Retain small structural contract checks only where useful, but add behavioral route tests for every mutation/read endpoint with hostile origin/auth/tenant/UUID/path/MIME/size/rate scenarios; exercise bounded preview failure with adversarial fixtures; capture and inspect responses and test logger output; and use PostgreSQL catalog/query-plan assertions for the performance-critical indexes. Generate the route matrix from an explicit inventory so new endpoints cannot silently escape coverage.

## Lower-priority observations

- **P2:** `apps/web/e2e/digital-products-accessibility.spec.ts:47-49` treats a visible `<body>` after CSS `zoom = 2` as proof of 200% usability; it does not assert reflow, horizontal overflow, clipping, focus visibility, or task completion at zoom. This should be strengthened, but the dedicated UX review should determine the complete accessibility disposition.
- **P2:** Fixture JSON is cast without runtime schema validation (`apps/web/e2e/digital-products.spec.ts:17-20`; `apps/web/e2e/digital-products-accessibility.spec.ts:20-25`). Add a shared validated schema, environment/protocol allowlist, and explicit non-production target assertion before credentials or state-changing acceptance actions are introduced.

## Positive observations

- The report and runbook truthfully state that real provider acceptance has not occurred and instruct operators to keep rollout disabled.
- Existing focused unit, integration, migration, and PostgreSQL concurrency suites provide meaningful coverage of many underlying invariants; the findings above concern the missing release-level proof, not a claim that those implementations are known broken.
- The runbook's rollback, repair, reconciliation, redaction, and leaked-link guidance is detailed and appropriately conservative.

## Round 2 Re-review — commit `0466edb`

### Verdict

**FAIL** — the prior behavioral-acceptance P1 remains, and two new release-interlock P1 issues prevent the new gate from serving as a trustworthy production promotion control.

### P1 — Required journeys still are not executed by Playwright

**Status:** Unresolved.

**Evidence:** `apps/web/e2e/digital-products.spec.ts:35-83` remains a collection of navigations to pre-seeded end-state URLs and broad text assertions. It still does not configure/publish a product, complete Stripe Checkout, observe Resend delivery, consume five grants and reject the sixth, replace a version, issue partial/full refunds, drive dispute transitions, inject/retry delivery, or invoke resend. Lines 85-100 replaced free-form phrases with JSON, but the test still trusts a hand-authored file: a scenario passes when it has a required ID, any provider-looking string, and any truthy `applicationState`. Neither the verifier (`scripts/verify-digital-products-acceptance.mjs:25-29`) nor Playwright checks provider events or authoritative application state against Stripe, Resend, or Supabase.

**Impact:** Fabricated or stale JSON can satisfy every non-browser transition while the actual production workflow is broken. Task 15 Step 2 and the Definition of Done remain unproven.

**Remediation:** Make the acceptance runner perform the transitions and generate evidence from observed provider/application results, or cryptographically/operationally obtain structured results from a trusted acceptance orchestrator and independently query provider and database state during verification. Validate exact expected state per scenario, unique event/order IDs, timestamps within the current run, linkage among event/order/manifest/job IDs, and the actual sixth-grant rejection—not merely field presence.

### P1 — The acceptance gate can test a different host than the fixture it validates

**Evidence:** `scripts/verify-digital-products-acceptance.mjs:20-24` validates `fixture.baseUrl` as non-production, but lines 32-34 never pass that URL to Playwright or compare it with `E2E_BASE_URL`. `apps/web/playwright.config.ts:3-5` independently defaults to `http://127.0.0.1:3000` and starts a local production build. Conversely, every route inside the fixture is accepted as an arbitrary string (`apps/web/e2e/digital-products.spec.ts:5-20`; `apps/web/e2e/digital-products-accessibility.spec.ts:6-25`) with no runtime schema, origin, protocol, or environment validation. Playwright `page.goto()` accepts absolute URLs, so individual fixture routes may point somewhere other than the validated `baseUrl`, including production.

**Impact:** The gate can validate one safe hostname while exercising another environment, or run the app locally against provider evidence from an unrelated deployment. It does not provide the claimed non-production safety or evidence/run provenance.

**Remediation:** Introduce one shared runtime schema for the entire fixture. Require all navigated URLs to resolve under the validated base origin, reject production hosts and credentials in fixture data, set `E2E_BASE_URL` from that validated origin (normally with `E2E_MANAGED_SERVER=false` for a deployed acceptance target), and bind evidence environment/run IDs to that origin and current execution.

### P1 — CI and database approval controls are not bound to the release they claim to gate

**Evidence:** The CI step is conditioned on `github.ref == 'refs/heads/main'` (`.github/workflows/ci.yml:53-64`). In a pull request into `main`, `github.ref` is a pull-request merge ref, so the acceptance step is skipped; it runs only on the post-merge push to `main`, after promotion has occurred. The database trigger queries only for any unrevoked, unexpired row (`supabase/migrations/20260813020000_digital_release_acceptance_gate.sql:23-34`). It never matches `release_version`, `environment`, or `evidence_sha256` to the deployed release/store operation. Review/provider timestamps can be future values, and expiry has no maximum bound (`:1-15`). Thus one generic long-lived `test`/`preview` approval authorizes every later store enablement and code release until its chosen expiry.

**Impact:** Neither control proves the code being promoted or enabled is the code that passed acceptance and review. Main can be merged before the gate runs, and stale/unrelated approval evidence can unlock rollout.

**Remediation:** Run a required acceptance workflow on the release-promotion PR (or a deployment promotion environment) before merge. Persist an immutable release identifier such as commit SHA/artifact digest and environment with the evidence; require the enable operation to provide/match that identifier and the intended production rollout approval. Constrain review/provider timestamps and approval lifetime, and document an audited break-glass path separately.

- The strict command now fails immediately when required files/provider variables are absent and explicitly requires Stripe test-mode keys.
